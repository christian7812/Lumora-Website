# Admin Product Management Design

## Intent

Let Cruiser Store administrators manage the catalog shown in the storefront. Today the admin Products page reads sample data, while the customer storefront reads active products from PostgreSQL. This workflow connects admin product create/edit/archive to PostgreSQL and normalizes the product category relationship so categories can be managed in the next workflow.

## Goals

- Admins can list all products, including archived products.
- Admins can create and edit product name, category, image URL, current price, optional old price, and active state.
- Admins can select from database-backed categories when creating or editing products.
- Existing products keep their category labels when migrated to a category table.
- Archiving hides a product from the storefront without removing historical order item data or changing existing product references.
- Every catalog write and admin catalog/category lookup requires a Better Auth session and an email in the comma-separated `ADMIN_EMAILS` allowlist.
- Existing public `GET /api/products` and checkout behavior continue to work, including the storefront's `category` string field.

## Non-goals

- Admin category create/edit/archive UI (the next workflow).
- Stock quantities and stock reservation (a later workflow).
- Image uploads; admins enter an image URL.
- Hard deletion, payment processing, or customer-facing product authoring.

## Constraints and current data

- `products.id` is text, products store `category` as text, prices are numeric strings, and `isActive` is boolean.
- Product IDs are seeded as numeric strings. New records use UUID strings generated by the server; the text primary key accepts both forms.
- Existing products can have multiple category labels. Migration must create one category per distinct trimmed current label and link every product to the matching row without dropping catalog data.
- Public product reads already filter to active products and return category labels. Keep the storefront response shape unchanged after the database normalization.
- Reuse one shared admin authorization helper for order and product endpoints so authorization rules do not drift.
- Keep the existing React, Refine, Shadcn UI, Express, Better Auth, Zod, and Drizzle stack; add no dependencies.

## Approaches considered

1. **Keep category labels as product text:** simplest and needs no data migration, but it cannot provide a reliable database-backed category selector or support the next category-management workflow cleanly.
2. **Normalize categories now (selected):** create a categories table, migrate existing distinct labels, and reference categories from products. This adds a migration and requires joining categories in product routes, but preserves current customer-facing responses and establishes the model for category management.

The normalized approach follows the user's choice to add a categories table and keeps category management as the next workflow.

## Proposed data and API behavior

- Add a `categories` table with UUID primary key, unique non-empty name, and active flag. Change `products.category` to `products.category_id` with a non-null UUID foreign key. Migration creates categories from distinct existing product labels, links every existing product, then removes the old text column.
- Add `GET /api/categories` for active category options. Add an admin-only category lookup that includes inactive categories only if product edit needs to preserve an existing inactive category; do not add category mutation endpoints in this workflow.
- Keep public `GET /api/products` response data as `{ id, name, category, image, price, oldPrice? }`; derive `category` from the joined category name so the storefront does not need a behavior change.
- Add admin-only `GET /api/products/admin`, `GET /api/products/:id`, `POST /api/products`, `PATCH /api/products/:id`, and `DELETE /api/products/:id`. Admin product responses include both `categoryId` and the category name. `DELETE` is a soft archive (`isActive = false`); edit can restore a product.
- Validate create/update bodies with Zod. Require a non-empty name, valid category UUID, HTTP(S) image URL, non-negative price, and optional non-negative old price greater than current price. The server creates UUID product IDs.
- Extract the order router's current admin check into a shared server helper and use it for admin product endpoints, preserving existing order endpoint authorization behavior.

## Proposed admin behavior

- Replace the admin Products sample table with Refine-backed data, loading/error/empty states, server-side pagination of 20 products per page, search across product name and category, active status, and Add/Edit/Archive/Restore actions.
- Add product create/edit routes and a form using existing Shadcn UI components. The category control loads database-backed categories; image entry remains a URL.
- Format prices as GH₵ and show archived products in the admin list while the storefront continues to hide them.
- Do not change the checkout request or order item product IDs.

## Acceptance checks

- Migration preserves every existing product and category label and creates one category row for each distinct label.
- Unauthenticated and non-admin requests cannot access admin product list or mutation endpoints.
- Admin create, edit, archive, and restore operations persist and appear correctly in the admin list.
- Archived products disappear from public `GET /api/products`; restoring them makes them visible again.
- Public product responses still provide `category` as a string, and checkout continues using the same product IDs and trusted database prices.
- Admin product pages handle loading, empty results, validation errors, and backend failures without rendering sample data.

## Builder calls

- Category CRUD is deferred to the next workflow; this slice creates and reads category rows only to establish the normalized model and populate product forms.
- Use soft archive through `isActive` because order items retain product IDs and names as historical records.
- Use server-generated UUID strings for new product IDs to avoid client-controlled identifiers while remaining compatible with the text primary key.
- Search both product name and category, and return 20 records per page with `x-total-count`, matching the existing order-list pagination convention.
